Finite state machines: Moore vs Mealy

A finite state machine (FSM) is a circuit that is always in exactly one of a fixed list of situations, called states. On each clock edge it looks at its inputs and decides which state to move to next.

Think of it like this: a board game. Your token sits on exactly one square (the state). Each turn you roll the dice (the input), and the rules say which square you move to (the transition). Some squares say "collect a prize" (the output).

Key terms

State
What the machine "remembers" about the past, e.g. "I have seen 1, 0 so far".
Transition
A move from one state to another, chosen by the current state and the input.
Output
The signal the FSM produces, e.g. "sequence found" or "light is red".
State diagram
A drawing: circles are states, arrows are transitions labelled with their conditions.
State table
The same information as the diagram, written as a table: current state + input → next state + output.
State encoding
Giving each state a binary number so it can be stored in flip-flops.
Reset state
The state the machine starts in (S0) when reset is 1.
Sequence detector
An FSM that watches a serial bit stream and raises an output whenever a fixed pattern (here 1011) has just gone past.
Failure function
The rule for where to go on a wrong bit: the state for the longest ending of what you have that is still a start of the pattern. It is what stops you throwing away partial progress.
Overlapping
A detector that may reuse the tail of one match as the head of the next. A non-overlapping detector must restart from scratch after every match.
Testbench
A simulation-only module that drives the design with a test stream and prints or plots what comes out. It never becomes hardware.

1. What an FSM is

Every FSM has three ingredients:

  1. States: a finite list. The machine is in exactly one at a time.
  2. Transitions: rules that use the current state + inputs to pick the next state.
  3. Outputs: signals the machine produces.

FSMs are everywhere: traffic lights, vending machines, elevators, washing machines, game AI (patrol → chase → attack), TCP network connections, USB handshakes and regex search engines. Even the CPU's own Fetch → Decode → Execute → Writeback loop is an FSM.

"Moore = output in the circle, Mealy = output on the arrow." Both styles can solve the same problems — Lab 8 (section 6) builds the same detector both ways so you can watch the difference in a waveform.

3. Anatomy of any FSM

Every FSM is built from three blocks: next-state logic (combinational gates), a state register (flip-flops), and output logic (combinational gates).

4. Example: a traffic light (Moore)

"The state diagram IS the design; everything else is just translating it to gates."

If you write Verilog instead of drawing gates, steps 5 and 6 collapse into one: a case statement is the state table, and the synthesiser does the K-maps for you. Lab 8 (next section) takes exactly that route.

Big picture: how a CPU uses FSMs

A CPU has a control unit (an FSM) and a datapath (registers, ALU, MUXes). Control sends control signals to the datapath; the datapath sends status flags (like "result is zero") back.

6. Lab 8: the "1011" sequence detector — four designs

The lab's task: one bit arrives on input in at each rising clock edge. Raise out when the pattern 1011 has just been seen. Two independent design decisions turn that one task into four legitimate, distinct hardware designs:

  1. Axis 1 · Mealy or MooreDoes the match signal come out combinationally on the transition (Mealy, same cycle), or only once the FSM settles into a dedicated "matched" state (Moore, one cycle later)?
  2. Axis 2 · Overlap or notAfter a match, may the trailing bits be reused as the start of the next candidate match, or must the search restart from scratch?
Why this is not a toy problem

Finding a fixed bit pattern in a live serial stream is the exact hardware task behind telecom frame synchronisation. The DS1/T1 superframe standard locates frame boundaries with the 6-bit sync pattern 001011 (and its rotations); SONET uses the framing byte 11110110. Any hardware that must find such a pattern — possibly with overlapping occurrences — is exactly the FSM you are building.

Shared test stream — use this for all four designs

IN = 1 0 1 1 0 1 1 0  (one bit per rising clock edge, bit 1 applied first)

  • Overlapping detectors must report 2 matches: bits 1–4, and bits 4–7 (bit 4 is reused).
  • Non-overlapping detectors must report 1 match: bits 1–4 only.

The failure-function method

All four designs share the same backbone, and the lab wants you to derive it the same way every time. Each state remembers how much of 1011 has been matched so far:

StateEncodingMeaning: the longest prefix of 1011 matched so far
S02'b00nothing matched yet
S12'b01matched 1
S22'b10matched 10
S32'b11matched 101 — one more 1 completes the pattern
S4 Moore only3'd4just matched 1011 → this is the state whose output is 1

The failure function is the rule for a wrong bit. Do not jump straight back to S0. Instead: write down the bits you have, append the new one, then find the longest ending of that string that is also a start of 1011. Go to the state for that ending.

  1. S1 (1) + input 1 → you now have 11. Its longest ending that starts 1011 is 1. → stay in S1.
  2. S2 (10) + input 0 → 100. Neither 0 nor 00 starts 1011. Nothing survives. → S0.
  3. S3 (101) + input 0 → 1010. Its ending 10 is a start of 1011. → S2, not S0. This is the one students get wrong.
  4. S3 (101) + input 1 → 1011. Match! What happens next is where the four designs split.
The shared backbone

Steps 1–3 are identical in all four designs. Only step 4 — where you go after a match — differs. Learn the backbone once and you have 90% of all four answers.

The whole lab in one picture: four designs, two edges

Across all four modules, the backbone (S0, S1, S2 and the climb to the deciding state) is letter-for-letter identical. Everything you are asked to explain comes down to one edge in each pair:

Simulating all four on IN = 10110110

Start: rst puts every machine in S0. Bits arrive in this order: 1, 0, 1, 1, 0, 1, 1, 0.

Bit 1 = 1: S0 + 1 → S1 (matched 1). All four agree. out = 0.

Bit 2 = 0: S1 + 0 → S2 (matched 10). out = 0.

Bit 3 = 1: S2 + 1 → S3 (matched 101). out = 0. One bit from a match.

Bit 4 = 1: MATCH. All four report it. Mealy raises out now, during this very cycle; Moore walks into S4 and raises out for the next cycle. The designs now diverge: Q1 → S1, Q2 → S0, Q3 → S4 (which behaves like S1), Q4 → S4 (which behaves like S0).

Bit 5 = 0: the overlapping machines are effectively at 1 + a 0 = 10 → S2: they are already two bits into a new match. The non-overlapping machines are at nothing + 0 → S0: still at zero.

Bit 6 = 1: overlapping go S2 → S3 (three bits in). Non-overlapping go S0 → S1 (one bit in).

Bit 7 = 1: second MATCH — but only for Q1 and Q3. They were in S3, so this 1 completes 1011. Q2 and Q4 were only in S1; for them this is just another 1 and they stay in S1. This single step is the entire overlap/non-overlap difference.

Bit 8 = 0: everything falls back to S2 (ending 10). Final tally: Q1 and Q3 found 2 matches, Q2 and Q4 found 1.

The one-paragraph write-up the lab asks for

Mealy vs Moore: the single structural change is where the output is produced. Mealy computes out inside the combinational block from state and input, so it rises in the same cycle as the final bit and needs no extra state. Moore drives out from the state register alone (assign out = (state == S4)), which forces a dedicated accepting state S4 — one more state, one more flip-flop, and the pulse arrives one clock later but is glitch-free and already registered.

Overlap vs non-overlap: the single structural change is the destination of one edge. Overlapping sends the machine to the state for the longest reusable suffix of the match (S1, because 1011 ends in 1); non-overlapping sends it to S0, discarding the tail. Everything else is untouched.

Lab correction — this testbench mis-reads the two Mealy designs

The four modules are correct. The testbench's sampling instant is not, for Mealy. The loop applies a bit at a falling edge and then prints out at the next falling edge — by which time the rising edge has already moved the state on, while in is still holding the old bit. For a Mealy machine, whose output is f(state, in) right now, that reads the wrong combination.

Simulating the whole thing cycle by cycle: Q1's printed lines show out = 1 against bits 3 and 6, not bits 4 and 7, and Q2's against bit 3, not bit 4. The hardware is fine — out really is high during the cycle in which bit 4 is applied (time 40–45 with this clock) — the printout just lands half a cycle late. Moore is unaffected, because its out depends only on the state, which is exactly what has settled by the falling edge; Q3 and Q4 print correctly on bits 4 and 7.

Fix: print before the rising edge instead of after it, so the Mealy output is read while its own bit is still the current one:

for (i = 7; i >= 0; i = i - 1) begin
    in = stream[i];
    #4;                                 // settle, still before the posedge at +5
    $display("bit=%b out=%b", in, out); // Mealy: correct instant
    @(negedge clk);
end

With that change Q1 prints pulses on bits 4 and 7 and Q2 on bit 4, matching the lab's stated results. If you would rather not touch the testbench, keep it and just read the waveform instead of the text: in the waveform Q1's pulse visibly covers the half-cycle during which bit 4 is applied, which is also what the deliverable's annotated screenshot is asking you to show.

Common mistakes & exam traps

Slips that cost marks
  • Read the question for the word "overlapping". Going to S0 after a match is wrong for an overlapping detector and right for a non-overlapping one. Both are correct hardware — for different specifications. Lab 8 exists to make you notice which one you were asked for.
  • Jumping to S0 on any wrong bit. Use the failure function: from S3 (101) a 0 gives 1010, whose ending 10 survives, so go to S2 — not S0. This mistake quietly loses matches and is the single most common one.
  • Mixing notations: Moore writes the output in the circle (S1/1); Mealy writes in/out on the arrow. Don't mix them in one diagram.
  • Miscounting states: Moore needs one more state than Mealy (5 vs 4 for 1011), because the output has to live somewhere.
  • Wrong flip-flop count: N states need ⌈log₂ N⌉ flip-flops. 5 states → 3, not 2.
  • Forgetting the reset state. Without reset, the machine may power up in a random state.
  • Unused codes (the three spare 3-bit codes in the Moore designs, or 11 in the traffic light) should route back to reset, so the machine can't get stuck. That is what default: next_state = S0; is for.
  • Missing default or default values in always @(*) creates accidental latches.
  • Writing out inside the always block of a Moore machine. If out can see in, it is a Mealy machine whatever you called it. Moore's output must be a single assign out = (state == S4);.
  • Trusting a printed simulation log without checking when it sampled. A Mealy output is only valid while its own input bit is still applied — see the lab correction above.

Practice

Moore or Mealy: the output changes in the same cycle the input changes. Which one is it?

Mealy, because its output depends on the input directly. A Moore output only changes when the state changes (one cycle later).

How many flip-flops for an FSM with 12 states?

⌈log₂ 12⌉ = ⌈3.58⌉ = 4 flip-flops (3 bits only give 8 codes).

Lab 8: both Q1 and Q3 report 2 matches on the shared stream, so what is the actual difference between them?

Timing, cost and glitch behaviour — not the answer.

  • Timing: Q1's pulse is high during the cycle in which bit 4 is applied. Q3's is high during the following cycle, after the edge that consumed bit 4. One clock apart.
  • Cost: Q1 needs 4 states / 2 flip-flops; Q3 needs 5 states / 3 flip-flops.
  • Quality: Q3's output comes straight off a flip-flop, so it is clean and already registered. Q1's comes through combinational logic from the input, so it can glitch if in glitches — and it must be sampled while its own bit is applied.

Rule of thumb: Mealy when you need the answer fast and cheap; Moore when you need it clean and easy to feed into the next block.

Lab 8: you change one line in moore_overlap.v to make it non-overlapping. Which line, and what to?

S4: next_state = in ? S1 : S2; becomes S4: next_state = in ? S1 : S0;

S4 stops mirroring S1 and starts mirroring S0. The in = 1 half looks unchanged, but that is only because S0 and S1 happen to agree there (a 1 always lands you in S1) — the whole row is now S0's row.

Trap: do not also change S3: next_state = in ? S4 : S2;. In a Moore machine the match edge always goes to S4, in both policies, because S4 is where the output lives.

Lab 8: in Q1's Verilog, why are next_state = S0; and out = 1'b0; written before the case?

To stop the synthesiser inferring a latch. Inside an always @(*) block, any path that leaves a signal unassigned is read as "hold its old value" — and holding a value needs memory, so the tool silently adds a latch you never asked for. Assigning a default first guarantees every signal gets a value on every path.

In Q1 the case happens to cover all four states anyway, so the next_state default is belt-and-braces. The out default is doing real work: only the S3 branch ever sets out to 1, and the other three branches rely on the default to make it 0.

Lab 8: the Mealy modules have no default: in their case, but the Moore ones do. Why?

It is about how many bit patterns the state register can hold. reg [1:0] state has 4 possible codes and the Mealy machines use all 4, so case is already exhaustive. reg [2:0] state has 8 codes and the Moore machines use only 5 — codes 101, 110 and 111 are unreachable in normal operation but physically possible after a glitch or at power-up. default: next_state = S0; guarantees the machine walks itself back into legal territory instead of getting stuck.

Lab 8: what does always @(posedge clk or posedge rst) give you that always @(posedge clk) does not?

An asynchronous reset. Listing posedge rst in the sensitivity list means the reset takes effect the instant it arrives, without waiting for a clock edge — useful at power-up, when the clock may not be running yet.

always @(posedge clk) with if (rst) inside gives a synchronous reset instead: it only acts on the next rising edge. Both are used in real designs; the lab chose asynchronous. Make sure the testbench holds rst high across at least one clock edge either way.

Lab 8: what is the longest run of input bits that can go by with no match, and what is the shortest gap between two matches?

No match, forever: a stream like 0000… or 1111… never produces a match, so there is no upper bound.

Shortest gap, overlapping: 3 bits. Once you have matched 1011, the next match needs 011 appended (giving 1011011) — the trailing 1 is reused. That is why Q1 and Q3 fire on bits 4 and 7 of the lab stream: exactly 3 bits apart.

Shortest gap, non-overlapping: 4 bits — a whole fresh copy of the pattern, e.g. 10111011 fires on bits 4 and 8.
