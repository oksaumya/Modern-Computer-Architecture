Von Neumann vs Harvard architecture

A computer is more than an ALU. It needs memory, I/O, and a way to wire them together. The lecture's question is: how exactly do these connect — and how many buses? Two classic blueprints answer it. Von Neumann keeps program and data in one memory on one bus. Harvard gives each its own memory and its own bus.

Think of it like this: a kitchen. In a von Neumann kitchen, the recipe book and the ingredients sit on one shelf, and the cook uses one door to reach it. The cook has to take turns: fetch the recipe, then fetch the flour. In a Harvard kitchen, recipes are on one shelf and ingredients on another, each with its own door. The cook can grab both at once.

Key terms

CPU
Central Processing Unit. The part that computes: control unit + ALU + registers.
Memory
The part that stores things. Each byte sits at a numbered place called an address.
I/O
Input/Output. How the computer talks to the world: keyboard, screen, disk, network.
Bus
A bundle of shared wires that connects the parts. It carries an address, data and control signals.
I-bus / D-bus
The lecture's names for the two Harvard buses: the instruction bus and the data bus.
Address space
The full range of numbered places. Von Neumann has one; Harvard has two separate ones.
Instruction
One small command for the CPU, e.g. "add these two registers". In MIPS it is a 32-bit number.
Stored-program concept
The program is kept in memory as numbers, just like data. To change the program, change the memory.
Bottleneck
The narrowest point that slows everything down, like the neck of a bottle.
Bus contention
Two jobs wanting the same wires at the same time. One has to wait.
IPC
Instructions Per Cycle. How much real work the CPU finishes each clock tick.
Throughput
How much gets moved or done per second. Harvard raises memory throughput by up to 2×.
Cache
A small, very fast memory (SRAM) next to the CPU that keeps copies of recently used bytes.
Microcontroller
A whole tiny computer on one chip (CPU + memory + I/O), e.g. the AVR chip on an Arduino.
DSP
Digital Signal Processor. A chip built to process audio, radio or sensor signals very fast.

1. From gates to a complete machine

Modules 1 and 2 built gates, adders, registers and FSMs. The lecture opens by zooming out: "A computer is more than an ALU — it needs memory, I/O, and a way to wire them together." Four parts, one question.

2. The stored-program concept (1945)

The lecture calls it "the radical 1945 idea: keep the program IN memory, as numbers, right alongside the data." It comes from John von Neumann's First Draft of a Report on the EDVAC, circulated in June 1945.

Before

Computers were wired for one task. Reprogramming meant rewiring by hand — on ENIAC, re-plugging cables and setting switches could take days.

After (von Neumann)

The program is stored in the same memory as the data, encoded as numbers. To run a different program you just load different numbers. Software as we know it was born.

One memory, two roles — the lecture's memory map

This is the exact picture from slide 06. Look at the Role column: nothing in the memory itself marks a word as "instruction" or "data". The role is decided purely by how the CPU reaches for it.

AddressContentsRole
0x00lw  r1, 0x40instr
0x04add r3, r1, r2instr
0x08sw  r3, 0x44instr
0x400x0000002Adata
0x440x00000000data

Reading it line by line:

  1. lw r1, 0x40 — load word: copy the 32-bit value living at address 0x40 into register r1. That value is 0x0000002A, which in decimal is 42 (2×16 + 10).
  2. add r3, r1, r2 — add r1 and r2, put the answer in r3.
  3. sw r3, 0x44 — store word: copy r3 out to address 0x44, overwriting the 0x00000000 that is sitting there.

Two details worth noticing. Addresses go up in 4s (0x00, 0x04, 0x08) because each instruction is 4 bytes = 32 bits. And the three instructions sit at low addresses while the data sits at 0x40 and 0x44 — same memory, same address space, just different neighbourhoods.

Slide correction: r2 is never given a value

The slide's map shows storage for the value loaded into r1 (at 0x40) and for the result (at 0x44), but r2 is never loaded from anywhere. As written, add r3, r1, r2 adds 42 to whatever junk r2 happens to hold. A complete version would need a fourth word of data and a second lw, e.g. lw r2, 0x48. The slide is making a point about layout, not about a runnable program — but don't copy it into an exam answer as a working snippet.

Note on notation: this lecture uses generic register names r1, r2, r3. From Lecture 11 onward the course switches to real MIPS names like $t0, $s1 — see MIPS registers & instruction formats.

How the CPU runs a stored program

  1. FetchRead the instruction at address PC from memory.
  2. DecodeWork out what it means (which operation, which registers).
  3. ExecuteDo it, e.g. add in the ALU, or read/write data in memory.
  4. NextPC ← PC + 4, then repeat forever.

PC means Program Counter: a register holding the address of the next instruction. PC + 4, again because instructions are 4 bytes. Module 4 builds this cycle in hardware (single-cycle datapath).

3. The key insight: programs ARE data

Slide 09. Because code lives in memory as numbers, it can be treated like any other data — and that unlocks four things you use every day.

λ  Compilers & assemblers

A program that writes another program. It outputs instruction-numbers as data into memory (or a file).

▤  Loading & the OS

The OS loads a program by copying its instruction-bytes into memory, then jumping to them.

⚡  Just-in-time compilation

JITs (the JVM, browser JavaScript engines) generate machine code while running and then execute it. Data becomes code.

⚠  Self-modifying code

A program can, in principle, rewrite its own instructions. Powerful, and a security minefield.

The lecture's own summary: "This blurring of code and data is von Neumann's superpower — and the root of whole classes of security exploits." Section 9 below follows that thread.

4. Von Neumann architecture

Slide 07: one memory, one bus — everything shares a single path between CPU and memory.

Good

  • Simple: one memory, one bus, one address space.
  • Flexible: any memory byte can be code or data.
  • Programs can load and create programs.

Bad

  • Bottleneck: code and data take turns on one bus.
  • A bug or attack can make the CPU run data as code.

5. The von Neumann bottleneck

Slide 12. Every instruction fetch and every data access share ONE bus, so they must take turns.

Where the name comes from (checked)

John Backus — the man who led the team that built FORTRAN — used the phrase "von Neumann bottleneck" in his 1977 Turing Award lecture, "Can Programming Be Liberated from the von Neumann Style?" (printed in Communications of the ACM, August 1978). His complaint was broader than wires: he argued the single word-at-a-time channel shapes how we are forced to think about programming, not just how fast the machine runs. The lecture's attribution is correct.

Four reasons it limits performance

Slide 13: "A fast CPU stalls whenever the bus is busy — computation waits on communication."

 ReasonWhat actually happens
⇄Bus contentionInstruction fetch and data access compete for the same wires. One must wait for the other.
◷Idle compute unitsWhile the ALU waits for the bus, it does nothing. Raw compute power sits unused.
▽Caps achievable IPCInstructions-per-cycle is limited not by the ALU but by how fast the bus delivers work.
↗Worsens with CPU speedFaster CPUs need data faster, but the bus doesn't scale as quickly. The gap grows.

The lecture's punchline: "The bottleneck is why caches, wider buses, and Harvard-style splits exist — all attempts to widen this pinch."

Slide correction: the stated growth rates don't match the drawn chart

The slide annotates its curves "CPU Demand grows ~60 % annually (Moore's Law)" and "Memory Bandwidth grows ~10 % annually". Compound those literally from 1980 to 2024 (44 years) and you get:

CPU  = 1.6044 = 9.6 × 108 ×
MEM = 1.1044 = 66 ×
gap  = 1.4 × 107 ×Both computed with python3. 60 %/yr crosses the chart's 10,000× ceiling in late 1999 — the dashed red line above.

The curve the slide actually draws reaches 7000× and 170×, which works out to about 22 %/yr for the CPU and 12 %/yr for memory, a 41× gap. So trust the picture, not the two annotations.

What are the real figures? The classic Hennessy & Patterson numbers are CPU ≈ 52 %/yr but only over 1986–2003, dropping to roughly 23 %/yr, then 12 %/yr, then a few %/yr as Dennard scaling ended; DRAM performance grew at about 7–9 %/yr. The "60 % vs 10 %" pair is a rule of thumb for the 1980s–90s window only. Quoting it for 44 straight years is what produces the impossible 109× above.

Also: "Moore's Law" is the wrong label for the CPU curve. Moore's Law is about the number of transistors per chip doubling (~every two years ≈ 41 %/yr), not about performance. Performance tracked it for a while thanks to Dennard scaling, then stopped.

The response: how architects fought back

  1. CachesKeep hot code & data on-chip, close to the core (Module 5).
  2. Wider / faster busesMove more bits per cycle.
  3. Harvard-style splitsSeparate paths for code and data.

The lecture then says: "The rest of today — and much of this course — is about that last idea." Module 5 picks up the first one (the memory wall & locality).

6. Harvard architecture

Slide 18: two memories, two buses — instructions and data never compete for the same path. The name comes from the Harvard Mark I (1944), which read its program from punched paper tape and kept data in separate counters.

Two buses, twice the throughput

Slide 19 and 21 make the payoff concrete. "What took two cycles now takes one."

The lecture is careful to add the price: "two memories and two bus systems — more wires, more pins, more silicon. Nothing is free."

Read "up to 2×" as a ceiling, not a promise

You only get the full doubling if every instruction also touches data memory. In real MIPS code only loads and stores do — typically about a quarter to a third of instructions. So the honest statement is the one the slide uses: up to 2× memory throughput. An exam answer that says "Harvard is always twice as fast" is wrong.

Where Harvard shines

Slide 22: "when predictable, high-throughput access matters more than flexibility."

∿  Digital signal processors

DSPs stream data through fixed algorithms (filters, FFTs). Parallel code + data fetch keeps the pipeline fed every cycle.

⚙  Microcontrollers

The ATmega328 (Arduino Uno) is true Harvard — Flash for code, SRAM for data, separate buses.

◷  Real-time systems

Deterministic timing matters. No bus contention means predictable, repeatable cycle counts you can actually guarantee.

▣  Embedded & IoT

Small fixed programs in Flash plus a little data in RAM map naturally onto the Harvard split.

The Arduino example, checked

The chip on an Arduino Uno is the ATmega328P (the P is the low-power variant). It has 32 KB of Flash for program, 2 KB of SRAM for data and 1 KB of EEPROM, with genuinely separate program and data buses and two separate address spaces — address 0x0100 in Flash and address 0x0100 in SRAM are different places. That is why an AVR needs a special instruction, LPM (Load Program Memory), just to read a constant string out of Flash: a normal load can only see SRAM. Strictly, that LPM back door makes the AVR a modified Harvard machine, but as a teaching example "true Harvard" is fair — unlike your laptop, the split is real silicon, not just a cache.

You will meet Harvard again in Module 4

The single-cycle MIPS datapath draws a separate instruction memory and data memory. That is a Harvard-style model, and it is exactly what lets one clock cycle fetch the instruction and read/write data at the same time (single-cycle datapath).

8. Modified Harvard: what your laptop actually is

Slide 25 puts it in one sentence: modern CPUs are von Neumann on the outside, Harvard on the inside.

Two levels, two answers

Outside the chip: one unified DRAM holds code and data — pure von Neumann. Simple, flexible, cheap.

Inside the chip: the L1 cache is split into a separate instruction cache (L1-I) and data cache (L1-D) — Harvard-style.

So the CPU fetches code and data in parallel from L1, but everything still lives in one memory underneath.

Best of both

Flexibility of von Neumann: one address space, code = data, easy to program and load.

Speed of Harvard: split L1 caches feed the pipeline code + data every cycle, with no contention.

A typical modern core has 32–64 KB of L1-I and the same of L1-D, per core.

Why this hybrid wins

Slide 27 gives four reasons — "it captures each architecture's strength exactly where that strength matters most."

 ReasonWhat it buys
⇉Parallel L1 accessSplit L1-I/L1-D lets the pipeline fetch an instruction and a data word every cycle — Harvard speed where it counts.
▤Unified main memoryOne DRAM address space keeps loading, linking and programming simple — von Neumann flexibility.
⚖Cache coherence handledHardware keeps the split caches consistent with unified memory, so software sees one memory.
★Scales to real workloadsGeneral-purpose speed and generality — which is why essentially every modern CPU does this.
The coherence catch that JITs hit

Keeping L1-I in step with L1-D is not fully automatic on every architecture. On x86 it effectively is. On ARM and RISC-V it is not: if a JIT writes new machine code through L1-D, the stale copy may still be sitting in L1-I, and the core would fetch the old bytes. That is why those ISAs have explicit cache-maintenance instructions (ARM's IC IVAU / DSB / ISB, RISC-V's FENCE.I) that a JIT must run before jumping into code it just generated. Module 6 covers coherence between cores (MESI).

9. Security: when data becomes code

The lecture flags this on slide 09 — "the root of whole classes of security exploits" — without following it up. Here is the thread, from the textbook.

In a von Neumann memory, the CPU cannot tell code from data. It runs whatever the PC points to. Attackers use this in a code-injection attack:

  1. InjectThe attacker sends input that contains machine-code bytes.
  2. OverflowA bug copies too much input, e.g. past the end of an array on the stack.
  3. HijackThe extra bytes overwrite a saved return address so it points at the injected bytes.
  4. RunWhen the function returns, the CPU jumps into the attacker's "data" and runs it as code.
The defence: the NX bit

NX means No-eXecute (Intel calls it XD, Windows calls the feature DEP). Every page of memory gets a flag. The OS marks the stack and the heap as writable but not executable, and the code as executable but not writable — a rule called W^X, "write XOR execute". If the PC jumps into an NX page, the CPU raises a fault and the OS kills the program. This brings a slice of Harvard's safety to a von Neumann memory, in software permissions rather than in wires.

Attackers adapted with return-oriented programming (ROP), which reuses code that is already executable, so address randomisation (ASLR) was added too. Module 6 covers hardware-level attacks (Spectre & Meltdown). Note that a true Harvard machine is immune to code injection by construction: there is no instruction that can write to instruction memory at all.

Common mistakes & exam traps

Slips that cost marks
  • The von Neumann bottleneck is about the single shared bus (and slow memory). It is not about having "only one CPU".
  • The term was coined by John Backus in 1977, not by von Neumann. Von Neumann described the architecture in 1945. Two different names, two different dates — examiners love swapping them.
  • Harvard does not mean "no stored program". Harvard machines still store the program in memory, just a separate one.
  • "Up to 2×" is a ceiling. Only load/store instructions use the D-bus, so the real gain is smaller.
  • Modern PCs are not pure Harvard. Only L1 is split; L2, L3 and DRAM are unified.
  • Harvard's cost is not just money: more wires, more pins, more silicon, and a fixed split you cannot re-balance.
  • "Moore's Law" is about transistor count, not CPU performance. Don't use it to label a performance curve.
  • The NX bit does not stop the buffer overflow itself. It stops the injected bytes from running.

Practice

What are the four parts of a computer, in the lecture's opening slide?

CPU (compute), MEMORY (store), I/O (talk to the world) and BUS (connect). The question that follows is: how do they connect, and how many buses?

State the stored-program concept in one sentence, and give its date.

Instructions are encoded as numbers and kept in memory alongside data, so the CPU fetches and runs them from memory, and a new program is loaded just by loading different numbers. 1945 — von Neumann's First Draft of a Report on the EDVAC. Before it, reprogramming meant rewiring by hand.

In the lecture's memory map, what decimal value sits at address 0x40, and what does lw r1, 0x40 do with it?

The word at 0x40 is 0x0000002A. 0x2A = 2×16 + 10 = 42. lw r1, 0x40 copies that 42 into register r1.

Why do the instruction addresses go 0x00, 0x04, 0x08? Each instruction is 4 bytes (32 bits) wide, so the next one starts 4 further along — the same reason the PC advances by 4.

Looking at that map, what is the role of the word at 0x44 before and after the program runs?

Before: it holds 0x00000000, an empty result slot. After sw r3, 0x44 runs, it holds whatever r3 computed. Either way the memory itself never labels it — the role comes from how the CPU reaches for it, not from the bits.

Name the four things "programs ARE data" makes possible.

Compilers & assemblers (a program that writes a program), the OS loader (copies instruction-bytes into memory, then jumps to them), JIT compilation (the JVM and browsers generate machine code at run time), and self-modifying code.

Who coined "von Neumann bottleneck", when, and what is it?

John Backus, in his 1977 Turing Award lecture ("Can Programming Be Liberated from the von Neumann Style?", printed in CACM 1978). The bottleneck: instruction fetches and data accesses share one bus to one memory, so they must take turns — never both in the same cycle — and the CPU computes far faster than that one bus can feed it.

Give the lecture's four reasons the bottleneck limits performance.
  1. Bus contention — fetch and data access compete for the same wires.
  2. Idle compute units — the ALU does nothing while it waits.
  3. Caps achievable IPC — instructions-per-cycle is limited by bus delivery, not by the ALU.
  4. Worsens with CPU speed — faster CPUs need data faster, but buses don't scale as quickly.
The slide says CPU demand grows ~60 %/yr and memory bandwidth ~10 %/yr. Over 1980–2024, what would that give — and is it right?

44 years of compounding: CPU = 1.6044 ≈ 9.6 × 108×, memory = 1.1044 ≈ 66×, a gap of about 1.4 × 107. That is absurd, and 60 %/yr would leave the slide's own 10,000× axis back in 1999.

The curve the slide actually plots ends at 7000× and 170×, i.e. about 22 %/yr and 12 %/yr and a 41× gap. The "60 %" figure is the classic Hennessy & Patterson rate (really ~52 %/yr) that held only from about 1986 to 2003; after that CPU growth fell to ~23 %, then ~12 %, then a few percent. Trust the drawn curve, not the annotation.

Three ways architects fought the bottleneck?

Caches (keep hot code and data on-chip — Module 5), wider and faster buses (more bits per cycle), and Harvard-style splits (separate paths for code and data). The third is what the rest of the lecture is about.

Harvard: how many cycles for "fetch an instruction and access data", and what is the speed-up?

One cycle instead of von Neumann's two, because the I-bus and D-bus are active at the same moment. The lecture says up to 2× memory throughput. "Up to" matters: only loads and stores use the D-bus at all, so in real code the gain is well under 2×.

The cost: two memories and two bus systems — more wires, more pins, more silicon.

The lecture's four places Harvard shines — and why each one wants it.
  • DSPs — stream data through fixed algorithms (filters, FFTs); parallel code+data fetch keeps the pipeline fed.
  • Microcontrollers — the ATmega328 on an Arduino Uno: Flash for code, SRAM for data, separate buses.
  • Real-time systems — no bus contention means predictable, repeatable cycle counts.
  • Embedded & IoT — a small fixed program in Flash plus small data in RAM maps straight onto the split.
Is an Arduino Uno von Neumann or Harvard? Give the numbers.

Harvard. The ATmega328P keeps the program in 32 KB of Flash and data in 2 KB of SRAM, on separate buses with two separate address spaces. Strictly it is slightly modified Harvard, because the LPM instruction exists purely so code can read constants out of Flash — a normal load can only see SRAM.

Why is your laptop called "modified Harvard"? Name the Harvard zone and the von Neumann zone.

Harvard zone (inside the chip): the CPU core plus the split L1-I and L1-D caches, each with its own path, so code and data arrive in parallel every cycle.

Von Neumann zone (from L2 outward): unified L2/L3 and one unified DRAM holding code and data in a single address space.

So: von Neumann on the outside, Harvard on the inside — flexibility underneath, Harvard speed where it counts.

Why can software still "see one memory" even though L1 is split?

Because hardware cache coherence keeps the split caches consistent with the unified memory below. Careful though: on ARM and RISC-V the instruction cache is not automatically coherent with the data cache, which is why a JIT must execute an explicit cache-maintenance instruction (FENCE.I on RISC-V) before jumping into code it has just written.

How does a code-injection attack use the stored-program concept, and what does the NX bit do?

The attacker's input (data) contains machine-code bytes. A buffer-overflow bug overwrites a saved return address so the PC jumps into that input, and because von Neumann memory does not separate code from data, the CPU runs it. The NX bit marks data pages (stack, heap) as non-executable, so the CPU faults instead of running the injected bytes. A true Harvard machine is immune by construction — nothing can write to instruction memory.
