MIPS32: registers and instruction formats (R, I, J)

MIPS32 has 32 registers, and every instruction is exactly 32 bits. Those 32 bits are cut into fields in one of only three layouts: R-type (register maths), I-type (a constant, memory, or a branch) and J-type (jump). The lecture's stated goal: "by the end you'll read a raw 32-bit hex instruction and write out the assembly it represents — by hand."

Think of it like this: a fixed-size postal form with boxes. Box 1 always says what kind of form (the opcode). The rest of the boxes depend on that kind: a "transfer" form has from, to, amount boxes; an "address change" form has one big box. The clerk (the CPU) reads box 1 first, then knows how to read the rest.
What this page covers, and from where

Lecture 11 — Registers & Instruction Formats gives the register conventions, the three bit layouts, and three worked activities (decode 0x02324820, hand-assemble addi $t0, $zero, 5, and the homework decode of 0x012A4020). Lab 11 — MIPS Assembly I (90 minutes, Anuj Kumar) adds the machine model, the syscall table, pseudo-instructions, mult/div with HI and LO, logic and shifts, scalar memory, a five-snippet bug hunt, and seven practice problems. Everything on this page below §9 is the lab. Every hex encoding here was recomputed field-by-field before it was written down.

Key terms

Register
A tiny, very fast storage slot inside the CPU. MIPS has 32 of them, each 32 bits wide — 128 bytes of storage in total.
Word
A 32-bit value (4 bytes) in MIPS.
Byte-addressed
Every byte of memory has its own address. So one word covers 4 addresses, and the next word is 4 further on.
Opcode (op)
The top 6 bits. They say which instruction (or which format) this is.
funct
The bottom 6 bits of an R-type. They pick the exact operation (add, sub, and…).
rs, rt, rd
5-bit register numbers (0–31). rs = first source, rt = second source (or the destination in I-type), rd = destination. The lab's framing: rs and rt are the register file's two read ports, rd is its write port — exactly the register file you built.
shamt
Shift amount: how many places to shift (for sll/srl/sra). 0 otherwise.
Immediate
A constant number stored inside the instruction itself (16 bits in I-type).
Sign extension
Widening a number by copying its top (sign) bit to the left, so −1 (FFFF) stays −1 (FFFFFFFF).
PC
Program Counter: holds the address of the instruction being fetched. Normally PC ← PC + 4. It is not one of the 32 registers and you never write it directly.
HI and LO
Two extra registers that catch the 64-bit result of mult and the quotient/remainder of div. You read them with mfhi and mflo.
Caller-saved / callee-saved
Who is responsible for preserving a register across a function call. $t = caller-saved (not preserved), $s = callee-saved (preserved). The lecture calls this "the single most-tested convention".
Pseudo-instruction
Something you are allowed to write that the CPU cannot run. The assembler silently replaces it with one or more real instructions (e.g. li, la, move, blt).
syscall
The one instruction that asks the simulator's operating-system layer to do something (print, read, exit). It is not an ALU operation.
Effective address
What lw/sw actually read or write: base register + sign-extended offset. In lw $t2, 4($t1) it is the value in $t1, plus 4.

1. The 32 registers

Each register has a number (0–31, used inside the machine code) and a name (used when you write code). The name tells you its job, by agreement between programmers — the calling convention. As the lecture puts it: "the hardware treats them equally, but software agrees on a role for each." You write $t0, but the machine code stores 8.

$t vs $s: the saving rules

The lecture flags this as "the single most-tested convention": who is responsible for preserving a register across a function call.

$t0–$t9 · temporaries

caller-saved

  • Not preserved across a call.
  • A called function may freely clobber them.
  • If the caller still needs the value, the caller must save it first.
  • Use for short-lived scratch values.

$s0–$s7 · saved

callee-saved

  • Preserved across a call.
  • A called function must restore them before returning.
  • The caller can trust they survive.
  • Use for values you still need after a call.
The lecture's mnemonic

t = "temporary, don't trust it"; s = "saved, it survives". You put this to work on the functions & stack page (Lab 14).

The special registers

  • $zero ($0) — the lecture calls it "the quiet hero". Hardwired to 0; reads always give 0 and writes are silently ignored. It buys you free instructions: move $t0,$t1 is "add zero to $t1", nop is "shift zero into zero", b L is "branch if 0 == 0".
  • $ra ($31) — the return address. jal writes "where to come back to" here so a function can return.
  • $sp ($29) — the stack pointer, tracking the top of the call stack for local variables and saved registers.
  • PC — not one of the 32. A dedicated register holding the address of the instruction being fetched. Updated automatically (PC ← PC + 4) or set by a branch, jump or call. You never write it like $t0.
  • HI and LO — also not among the 32. They hold the results of mult and div: see §9.6.
Link to Module 2

These 32 registers are the register file you built: 32 × 32-bit registers, 2 read ports (for rs and rt) and 1 write port (for rd or rt). Reads are instant (combinational); writes happen on the clock edge. The $zero register is wired to 0.

Memorise the numbers with ranges

0 zero · 1 at · 2–3 v · 4–7 a · 8–15 t · 16–23 s · 24–25 t · 26–27 k · 28 gp · 29 sp · 30 fp · 31 ra. Fast check: $t0 = 8, $s0 = 16, $ra = 31.

2. The machine model: two boxes and a narrow road

Lab 11 opens with this picture, and the whole ISA follows from it. There are only two boxes — the CPU and memory — and everything that happens is traffic between them.

Load/store architecture: c = a + b costs four instructions

Because only registers reach the ALU, a one-line sum in a high-level language becomes four MIPS instructions.

MIPS · c = a + bcode → what it means
lw $t0, a1 — copy the value of the variable a from memory into a register.
lw $t1, b2 — same for b. Now both operands are inside the CPU.
add $t2, $t0, $t13 — the actual addition. Register + register → register. Destination comes first.
sw $t2, c4 — copy the answer back out of the register into memory at c.
Illegal, and why

add $t0, var, $t1 does not assemble. The operands of add are registers, full stop. x86 lets an ALU instruction read memory directly; MIPS does not, and that restriction is exactly what buys the fixed 32-bit format, the fast decode and the simple pipeline.

Fetch, decode, execute: the loop the CPU never stops

  1. 1 FetchWord at address PC → instruction register. PC ← PC + 4.
  2. 2 DecodeSplit op / rs / rt / rd / funct. Read the two registers.
  3. 3 ExecuteALU: add, sub, and, or — or compute a memory address.
  4. 4 Memorylw reads, sw writes. Everything else skips this stage.
  5. 5 Write backResult → rd (R-type) or rt (I-type).
InstructionFetchDecodeExecuteMemoryWrite backNote
add $t2,$t0,$t1••••no memory access
lw $t0,4($t1)•••••the only instruction that uses all five
sw $t0,4($t1)••••nothing to write back
beq $t0,$t1,L•••may replace PC

These are the same five stages as the single-cycle datapath and the 5-stage pipeline. Fixed 32-bit instructions make stage 1 trivial: the next instruction is always at PC + 4.

3. Memory: bytes, words, and "×4"

Every instruction is 32 bits, and memory is byte-addressed. So one word takes 4 addresses, and words sit 4 bytes apart. That is why the PC moves by 4, and why array element A[8] is at offset 8 × 4 = 32.

In MARS: the program (.text) starts at address 0x00400000, data (.data) starts at 0x10010000, and $sp starts at 0x7FFFEFFC. The lab's advice is to read these off the simulator's text and data panes rather than memorise them, since another simulator may choose differently.

Alignment: a word address must be a multiple of 4

If you ask for a word at an address that is not a multiple of 4, the CPU raises an address error exception — the program stops. lb/sb (single bytes) have no such restriction.

Endianness: which end of the word comes first

Store the word 0x12345678 at address B. Which byte lands at B+0?

OrderB+0B+1B+2B+3lb $t1, 0($t0) gives
Big-endian (most significant byte first)123456780x12
Little-endian (least significant byte first)785634120x78

MIPS hardware is bi-endian — the chip can be wired either way, and your simulator picks one. Network byte order is big-endian; x86 is little-endian. (MARS is little-endian.) It only matters when you read a word one byte at a time.

4. The three instruction formats

All three formats put the opcode in the top 6 bits, and put rs and rt in the same place. The CPU reads the opcode first to know which layout follows — that regularity is what makes the decoder simple and fast.

R-type: op(6) rs(5) rt(5) rd(5) shamt(5) funct(6)

op is 0 for every R-type. The funct field chooses the operation. The result goes into rd. How the lecture says to read one: opcode = 0 → R-type; funct → the actual operation; rs, rt → the two sources; rd → the destination; shamt → shift amount (0 unless it is a shift).

Sign-extend or zero-extend? (Lab 11, "three details every student gets wrong once")

The 16-bit immediate must be widened to 32 bits before it is used.
Sign-extended: addi addiu lw sw lb slti and branch offsets. Range −32768 to +32767. addi $t0,$t0,-1 stores 0xFFFF, which widens to 0xFFFFFFFF.
Zero-extended: andi ori xori, because logic works on bit patterns, not on magnitudes. andi $t0,$t1,0xFFFF masks with 0x0000FFFF, not with 0xFFFFFFFF.
Same idea one size down: lb on the byte 0xF0 gives 0xFFFFFFF0, while lbu gives 0x000000F0.

"Unsigned" is a misnomer — the lab's Sheet-K clarification

addu / addiu do exactly the same arithmetic as add / addi, on exactly the same bits. The only difference is that they do not trap on overflow. Concretely: 2³¹ − 1 = 2,147,483,647 = 0x7FFFFFFF; adding 1 with add raises an exception, while addu quietly returns 0x80000000 = −2,147,483,648. And despite the "u", addiu's 16-bit immediate is still sign-extended.

Constants bigger than 16 bits need two instructions: lui loads the upper 16 bits, then ori fills in the lower 16. Example: lui $t0, 0x1001 then ori $t0, $t0, 0x0000 makes $t0 = 0x10010000. The la (load address) pseudo-instruction does exactly this — which is why it costs two real instructions, not one.

J-type: op(6) address(26)

j (op 0x02) and jal (op 0x03) store a 26-bit word address. jal additionally writes PC + 4 into $ra — that is what makes it a function call. The CPU builds the full 32-bit target like this:

Target = { (PC+4)[31:28] , address , 00 }Take the top 4 bits of PC+4, then the 26-bit field, then two 0 bits (every instruction address is a multiple of 4). { } means "join the bits together". Equivalently: target = ((PC+4) & 0xF0000000) | (address << 2).
Slide correction

Lecture 11 slide 20 writes the rule as target = (PC[31:28]) | (address << 2), using the current PC. The hardware actually takes the top 4 bits of PC + 4 (the already-incremented PC), as MIPS32 and Patterson & Hennessy both specify. In almost every exam question the two give the same answer, because the top 4 bits only differ when the jump sits in the last word of a 256 MB region — but write PC + 4 and you are right in every case. The slide is correct about the important part: the << 2, and the 256 MB reach.

So j can only reach addresses in the same 256 MB block as PC+4 (same top 4 bits). To jump anywhere, use jr with a full 32-bit register.

5. Worked encodings — the class's own examples

Lab 11's phrase for this is "be the assembler". The recipe never changes: map the written operands onto the field names, write each field in binary at its exact width, regroup into 4s, read off hex.

Encoding 1: add $t2, $t0, $t1 (R-type) — Lab 11, "be the assembler"

  1. Map the operands. Written add rd, rs, rt, so rd = $t2 = 10, rs = $t0 = 8, rt = $t1 = 9.
  2. Fill the fields. op = 0 (every R-type), rs = 8, rt = 9, rd = 10, shamt = 0, funct = 32 (0x20).
  3. Write each field in binary, at its width. 000000 01000 01001 01010 00000 100000
  4. Regroup into 4s. 0000 0001 0000 1001 0101 0000 0010 0000
  5. Each group is one hex digit: 0x01095020.

The lab's point: "the CPU never sees $t2 or the word 'add'. It sees bits. The program is a list of 32-bit numbers in memory."

Encoding 2: decode 0x02324820 (Lecture 11, Activity 2)

  1. Hex → binary, 4 bits per digit: 0000 0010 0011 0010 0100 1000 0010 0000
  2. Read the top 6 bits. op = 000000 → R-type, so slice 6 | 5 | 5 | 5 | 5 | 6.
  3. Split: 000000 | 10001 | 10010 | 01001 | 00000 | 100000
  4. Translate: rs = 10001 = 17 = $s1, rt = 10010 = 18 = $s2, rd = 01001 = 9 = $t1, shamt = 0, funct = 0x20 = add.
  5. Write it in assembly order (rd first): add $t1, $s1, $s2, i.e. $t1 = $s1 + $s2.

Encoding 3: hand-assemble addi $t0, $zero, 5 (Lecture 11, Activity 3)

  1. Identify the format. addi is I-format. op = 0x08 = 001000.
  2. Map: written addi rt, rs, imm, so rt = $t0 = 8 (destination), rs = $zero = 0, imm = 5.
  3. Place the bits. 001000 00000 01000 0000000000000101
  4. Regroup to hex. 0010 0000 0000 1000 0000 0000 0000 0101 = 0x20080005.

In practice an assembler writing li $t0, 5 emits addiu (op 0x09) instead, giving 0x24080005 — same arithmetic, no overflow trap. See §9.5.

Encoding 4: decode 0x8D280004 (Lab 11, "reverse it")

  1. Binary: 1000 1101 0010 1000 0000 0000 0000 0100
  2. op = 100011 = 35 = 0x23 → lw, which is I-format, so slice 6 | 5 | 5 | 16.
  3. Split: rs = 01001 = 9 = $t1 (the base), rt = 01000 = 8 = $t0 (the destination), imm = 0000000000000100 = 4 (a byte offset).
  4. Answer: lw $t0, 4($t1) — "load into $t0 the word at address $t1 + 4".
Which register receives the data?

rt. I-type has no rd field, so for loads the destination sits in the rt slot. This is the question the lab asks on the slide, and the one that catches people in the exam.

Encoding 5: the 30-second drill — addi $t2, $t3, 5

op = 001000, rs = $t3 = 11 = 01011, rt = $t2 = 10 = 01010, imm = 5.
001000 01011 01010 0000000000000101 → 0010 0001 0110 1010 0000 0000 0000 0101 = 0x216A0005.

Two traps hidden in that table
  • Negative immediates: write the 16-bit two's complement and nothing more. −1 = FFFF, −8 = FFF8, −12 = FFF4. Do not write a 32-bit pattern into a 16-bit field. At run time the CPU sign-extends it back.
  • sll swaps the usual roles: the register being shifted goes in rt, and rs is 0. In jr it is the opposite — the register goes in rs, and rt, rd, shamt are all 0.

6. Branch offsets (beq / bne)

A branch does not store the full target address. It stores how many instructions to jump, counted from PC + 4 (the instruction after the branch). The count can be negative, to jump backwards.

offset = (Target − (PC + 4)) ÷ 4   ⇔   Target = PC + 4 + offset × 4PC = address of the branch itself. The offset is a signed 16-bit number of instructions (words), not bytes.
AddressCodeMachine codeNote
0x00400000loop: beq $t0, $zero, exit0x11000002(0x0040000C − 0x00400004) ÷ 4 = 2

beq decoded: op 4 = 000100, rs = $t0 = 8 = 01000, rt = $zero = 00000, offset = 2 → 0001 0001 0000 0000 0000 0000 0000 0010 = 0x11000002.

Backward example: a bne $s3, $s4, loop at 0x0040002C with loop at 0x00400000: offset = (0x00400000 − 0x00400030) ÷ 4 = −48 ÷ 4 = −12 = 0xFFF4. Machine code 0x1674FFF4.

Why count in instructions? (the lecture's "forgetting the << 2")

Targets are always multiples of 4, so the bottom two bits would always be 00 — wasted. Storing the count ÷ 4 gives 4× the reach: ±32768 instructions (about ±128 KB) instead of ±32 KB. The hardware shifts it back left by 2 before adding. Miss the << 2 and every branch and jump target you compute is wrong by a factor of 4.

7. Decoding: hex back to an instruction

  1. Hex → binaryWrite 4 bits per hex digit.
  2. Read opTop 6 bits. 0 means R-type; 2 or 3 means J-type; anything else is I-type.
  3. Split fieldsUse that format's layout.
  4. Look upfunct (R) or op (I/J); register numbers → names.
  5. Write itIn the written order (R: rd, rs, rt).

Example: decode 0x01098022

  1. 0000 0001 0000 1001 1000 0000 0010 0010
  2. op = 000000 → R-type. Split: 000000 | 01000 | 01001 | 10000 | 00000 | 100010
  3. rs = 8 ($t0), rt = 9 ($t1), rd = 16 ($s0), shamt = 0, funct = 34 = 0x22 → sub
  4. Answer: sub $s0, $t0, $t1
Decoding in code, not on paper

Lab 11 points out that the same job is just a shift: srl $t1, $t0, 26 moves the opcode field down to the bottom, so 0x8D280004 >> 26 = 35 = lw. Masks and shifts are how a real decoder (and your single-cycle datapath) pulls the fields apart.

Addresses step by 4 because every instruction is 32 bits. Some assemblers emit ori $t0,$zero,7 (0x34080007) for li instead of addiu; both are correct, and your simulator's text pane tells you which one yours chose.

Program and data share one memory

Instructions live in .text, variables in .data, but they are the same bytes in the same address space. The CPU cannot tell them apart by looking at the bits — only PC versus lw/sw decides which is which. That is the stored-program (von Neumann) idea, and it is why forgetting the exit syscall makes the CPU happily start executing your string data.

Why this matters for what comes next: loops and function calls are nothing more than instructions that put a different value into PC.

9. Lab 11: writing and running MIPS in MARS

Lab 11 (MIPS Assembly I: Machine, Arithmetic & Memory) is the 90-minute lab that turns the bit layouts above into programs you can run. Its own summary of what you should be able to do by the end: explain fetch/decode/execute and what PC does; name the registers by convention and use only $t, $a, $v, $zero; write a .data/.text program that reads, computes, prints and exits via syscall; use add/sub/addi and mult/div with HI/LO; tell la (an address) from lw (a value); and encode and decode one R-type and one I-type by hand.

It is an open-book lab

Both reference sheets stay open for all 90 minutes — the JHU CS333 quick reference ("Sheet J": conventions, the syscall table, worked examples) and the KTH reference sheet v1.12 ("Sheet K": exact semantics, opcode/funct numbers, bit formats). Memorise nothing. Understand everything. When the two sheets disagree, Sheet K is the hardware truth and Sheet J is the assembler's convenience — and the simulator is the final judge.

9.1 The workflow: edit → assemble → run → inspect

  1. Write one .asm file. .data section first, then .text, then .globl main and a main: label.
  2. Assemble. MARS turns your text into 32-bit words. Errors appear in the message pane with a line number — fix the first one, then re-assemble, because one bad line often causes several complaints.
  3. Run, or single-step. Run goes straight to the end; single-step executes one instruction and stops, which is what you want while you are still learning.
  4. Inspect. Watch the Registers pane (changed values are highlighted), the Text segment pane (address, machine word and your source, side by side) and the Data segment pane (your .data, starting at 0x10010000).
  5. Reset before re-running. Otherwise you start with the previous run's register values, and a bug can look fixed when it is not.
Where to look for each thing

The Text segment pane is the single most useful view on this page's material: it shows, for every line you wrote, the address, the 32-bit machine word in hex, and — for a pseudo-instruction — the real instruction(s) the assembler substituted. That is how you check an encoding you worked out by hand, and how you see that la really did cost two instructions.

Four things that bite in the simulator
  • Forgetting the exit syscall. Without li $v0, 10 / syscall the CPU keeps fetching the next bytes in memory and tries to execute your data.
  • Running without resetting. Registers keep their old values, so a bug looks fixed when it is not.
  • Stale $v0. Every syscall reads $v0 to pick the service. Set it immediately before each one.
  • Output text that does not match exactly. The lab's auto-grader fails on one stray space or newline; match the starter code's output text character for character.

9.5 Pseudo-instructions: what you write vs what the CPU runs

Several of the most convenient instructions do not exist in hardware. The assembler expands them, usually using $at as scratch — which is exactly why you must never use $at yourself.

Consequence: count the real instructions

9.6 Arithmetic, and the HI/LO pair

MIPS · x = (a + b) − c, with a=7, b=3, c=4code → what it means

There is no subi

To subtract a constant, add a negative one: addi $t0, $t0, -1. The hardware sign-extends the 16-bit 0xFFFF back to −1.

Multiplication and division do not write a normal register. They write the two special registers HI and LO, and you fetch the halves you want with mfhi ("move from HI") and mflo.

9.7 Logic and shifts: bits in, bits out

Take $t0 = 1100 1010 (0xCA) and $t1 = 0000 1111 (0x0F), shown here as 8-bit patterns for readability:

InstructionResult (8-bit view)HexWhat it does

nor $t2,$t0,$t10011 00000x30NOT(OR): 1 only where both are 0.
Careful with the 8-bit view

The nor row is the honest answer for 8-bit registers. In a real 32-bit MIPS register, $t0 = 0x000000CA and $t1 = 0x0000000F, so nor $t2,$t0,$t1 actually gives 0xFFFFFF30 — the top 24 bits were 0, and NOR turns them into 1s. and, or and xor are unaffected because their upper bits stay 0. The lab's table says "8-bit view" for exactly this reason.

InstructionStarting valueResultMeaning
sll $t1,$t0,30x0000000F0x00000078Shift left 3 = multiply by 2³: 15 × 8 = 120.

Idioms the lab says you will reuse:

  • andi $t1, $t0, 1 — keep only bit 0. 1 means odd, 0 means even (Lab 13's even/odd problem).
  • sll $t1, $t0, 2 — multiply an array index by 4 to turn it into a byte offset (Lab 12's arrays).
  • nor $t1, $t0, $zero — bitwise NOT, since NOT(x OR 0) = NOT x.
  • srl $t1, $t0, 26 — slide the opcode field down to the bottom of the register, so you can read it as a plain number.
srl vs sra is the classic mix-up

srl zero-fills, sra sign-fills. On a negative number they give wildly different answers, as the table above shows.

9.8 Scalar memory: la gives the address, lw the value, sw writes

The classic memory bug

10. Lab 11 bug hunt: five broken snippets

The lab's pair exercise. For each one: find the bug, state the symptom, fix it in one line. The lab's debugging order, used all semester: (1) read the symptom, (2) write the trace table, (3) find the first row that differs from what you expected, (4) fix that line only.

S1 — prints nothing, or something bizarre. li $a0, 42 then syscall

Root cause: $v0 was never set, so syscall runs whatever service number happened to be left in it.

Fix: add li $v0, 1 before the syscall. The three-beat pattern is service, argument, call — in that order, every time.

S2 — prints a huge number, not 42. x: .word 42 … la $a0, x / li $v0, 1 / syscall

Root cause: la loads the address of x; print-integer then prints that address (something like 268500992).

Fix: lw $a0, x — load the value.

S3 — prints 0, wanted 42. li $t0,6 / li $t1,7 / mult $t0,$t1 / li $v0,1 / move $a0,$t2 / syscall

Root cause: mult writes HI and LO, not a general-purpose register. $t2 was never assigned, so it still holds 0.

Fix: add mflo $a0 after the mult (or mflo $t2, keeping the move). 6 × 7 = 42, and 42 fits in 32 bits so HI is 0.

S4 — quotient and remainder swapped. div $t0,$t1 (17 ÷ 5) / mfhi $s0 / mflo $s1

Root cause: the roles are reversed. LO holds the quotient (3) and HI holds the remainder (2).

Fix: mflo $s0 ; mfhi $s1.

S5 — address error. la $t0, x / lw $t1, 2($t0)

Root cause: a word load at an address that is not a multiple of 4. x is word-aligned, so x + 2 is not, and the CPU raises an address error exception.

Fix: use offsets 0, 4, 8… for lw/sw. If you genuinely want the byte at x + 2, use lb (or lbu).

12. The same model, refined: RISC-V

Lecture 11 closes by mapping everything above onto RISC-V, because the transferable skill is the register-and-format model, not the syntax. RV32I is a minimal 32-bit integer base: about 40 instructions, 32 registers x0–x31 (with x0 hardwired to zero, exactly like $zero), fixed 32-bit instructions, load/store only.

The six extension letters you bolt onto the RV32I base: M multiply/divide · A atomic operations · F single-precision float · D double-precision float · C compressed 16-bit instructions · V vector (SIMD). So RV32IMAFD = base + multiply + atomics + float + double. Pick your letters, get your ISA. More on the philosophy behind this on the CISC vs RISC page.

Common mistakes & exam traps

The lecture's own six
  • Writing to $zero. It is hardwired to 0 and writes are silently ignored. Never use it as a destination.
  • Forgetting PC + 4. Instructions are 4 bytes, the PC advances by 4, and branch targets are measured from PC + 4.
  • Skipping sign extension. The 16-bit immediate is sign-extended to 32 bits: 0xFFFB is −5, not 65531.
  • Confusing rd, rs, rt. In R-format rd is the destination; rs and rt are the sources. The order in the binary is rs rt rd — it is not the order you write them.
  • $t vs $s saving. $t is caller-saved (not preserved), $s is callee-saved (preserved). Do not swap them.
  • Forgetting the << 2. Branch and jump offsets are counted in words and shifted left 2 to make bytes. Miss it and every target is wrong by 4×.
Plus the ones from Lab 11 and the encoding drills
  • In lw/addi, the destination is rt, not rd — I-type has no rd field.
  • In sll, the source register goes in rt and rs = 0. In jr, the register goes in rs.
  • Negative immediates: write the 16-bit two's complement (−1 = FFFF, −8 = FFF8). Don't write 32 bits into a 16-bit field.
  • Decimal where hex is expected: funct for add is 32 decimal = 0x20.
  • Register numbers: $t0 is 8 (not 0), $s0 is 16, $sp is 29, $ra is 31.
  • LO is the quotient, HI is the remainder. And mult/div write neither to a normal register until you run mflo/mfhi.
  • la gives an address, lw gives a value. Printing the former gives a huge meaningless number.
  • A word load or store needs an address that is a multiple of 4, or you get an address-error exception.
  • srl zero-fills, sra sign-fills — only sra is a correct signed divide by a power of two.
  • Count real instructions: la, bge, blt, ble and a big li are two each.
  • Never touch $at — the assembler is already using it to build your pseudo-instructions.

Regroup in 4s: 1000 1111 1010 1001 0000 0000 0001 0000 = 0x8FA90010.

Watch the slice. The lecture's slide shows these same fields but writes the hex nowhere — a common slip is to read the rs field as 11101 and then forget that its top bit lands in the second hex digit (giving 0x8D… instead of 0x8F…). Always regroup the full 32 bits in fours before converting.

Homework 3. Explain the difference between $t-registers and $s-registers in the calling convention.

$t0–$t9 are caller-saved temporaries: a function you call is free to destroy them, so if you still need a value after a call, you (the caller) must save it first. $s0–$s7 are callee-saved: any function that wants to use one must save the old value on the stack and restore it before returning, so the caller can trust the value survives.

Practical rule: short-lived scratch values go in $t; anything you still need after a jal goes in $s. The hardware enforces none of this — it is a pure agreement between programmers, which is why it is a convention.

Exit ticket (L11) 1. Which fields does the R-format have, in order?

op(6) | rs(5) | rt(5) | rd(5) | shamt(5) | funct(6) — from bit 31 down to bit 0, adding up to exactly 32.

Exit ticket (L11) 2. What value does $zero always hold, and what happens if you write to it?

It always reads as 0 — it is hardwired, not merely initialised. A write to it is silently ignored: no error, no change, the program carries on. That is what makes it safe to use as the "throw away the result" destination and as a free source of the constant 0.

Exit ticket (L11) 3. Name the six RISC-V extension letters and what each adds.

M integer multiply and divide · A atomic memory operations · F single-precision floating point · D double-precision floating point · C compressed 16-bit instruction encodings · V vector (SIMD). They bolt onto the RV32I base, so RV32IMAFD names a specific chip's ISA.

Exit ticket (Lab 11) 1. lw $t0, 4($t1) with $t1 = 0x1000. What is the effective address?

Effective address = base register + sign-extended offset = 0x1000 + 4 = 0x1004. It is a multiple of 4, so the load is legal.

Exit ticket (Lab 11) 2. After div $t0, $t1, which instruction gives you the remainder?

mfhi — the remainder is in HI. mflo would give you the quotient.

Exit ticket (Lab 11) 3. la $t0, x versus lw $t0, x: which one puts 10 in $t0 when x: .word 10?

lw. It loads the value stored at x. la loads the address of x — a number around 0x10010000, which prints as something like 268500992.

Cold call. Why can't you write add $t0, var, $t1?

MIPS is a load/store architecture: the ALU's operands come from registers only. To use a variable in memory you must lw it into a register first. That restriction is what keeps every instruction 32 bits and the decode fast.

Cold call. Which pipeline stages does add skip? And sw?

add skips Memory (it never touches memory): Fetch, Decode, Execute, —, Write back. sw skips Write back (there is no register result): Fetch, Decode, Execute, Memory, —. Only lw uses all five.

Cold call. 13! does not fit in 32 bits. What does LO hold, and where do you see the overflow?

13! = 6,227,020,800. In HI:LO that is HI = 0x00000001, LO = 0x7328CC00. LO alone reads 1,932,053,504 — a perfectly plausible-looking wrong answer. The only sign anything went wrong is that HI is not 0 (for a positive product). This is exactly why Lab 13's "factorial of any number" has to check HI, and why the single-instruction mul rd, rs, rt — which discards HI — cannot warn you.

Cold call. Why is li $t0, 0xabcd1234 two instructions?

The I-type immediate field is only 16 bits wide, so no single instruction can carry a 32-bit constant. The assembler emits lui $at, 0xabcd (upper half into the top 16 bits) then ori $t0, $at, 0x1234 (lower half OR-ed in). ori rather than addi because ori zero-extends — addi would sign-extend 0x1234's cousin 0x8234 and corrupt the upper half.

Cold call. Which R-type fields map onto the register file's ports?

rs and rt are the two read ports; rd is the single write port. That is precisely the 2-read / 1-write register file you built in Module 2 — the instruction format was designed around the hardware, not the other way round.

op = 8, rs = rt = 29 (11101), imm = −8 = 0xFFF8.

Drill. Decode 0x1674FFF4. If it sits at address 0x0040002C, where does it jump?

000101 10011 10100 1111111111110100: op 5 = bne, rs = 19 ($s3), rt = 20 ($s4), offset = −12.
bne $s3, $s4, …. Target = 0x0040002C + 4 + (−12 × 4) = 0x00400030 − 0x30 = 0x00400000.

Drill. A jal func has the address field 0x0100012 and sits at 0x0040001C. What is the target, and what goes into $ra?

Target = {(PC+4)[31:28] = 0000, 0x0100012, 00} = 0x0100012 × 4 = 0x00400048. $ra = PC + 4 = 0x00400020. (The factorial program on the functions page has exactly these numbers in the simulator.)

Drill. Why do andi/ori zero-extend but addi sign-extends?

Logic operations treat the constant as a bit pattern — a mask — so the bits you did not write should be 0. addi does arithmetic, so a negative constant must stay negative, which needs sign extension.

Drill. How many bits hold a register number, and why?

5 bits, because 2⁵ = 32 registers. (And that is why the ISA has 32 and not 40: three 5-bit fields plus a 6-bit opcode and a 6-bit funct is exactly 32.)

Drill. What 32-bit value does lui $t0, 0x1001 put in $t0?

0x10010000: the immediate goes into the upper 16 bits and the lower 16 bits are 0. (That is the start of the simulator's data segment.)
