The memory wall & locality

The CPU is far faster than main memory, so it often sits waiting for data. The fix is a hierarchy: small, fast memories close to the CPU hold the data it is likely to need next. This works because programs have locality. They keep reusing the same data and the data next to it.

Think of it like this: you are cooking. The spice rack by the stove is the cache: small, but within arm's reach. The kitchen cupboard is main memory: bigger, but a few steps away. The shop down the road is the disk: huge, but a long trip. You keep what you are using right now on the rack, and it works because a recipe uses the same few spices again and again.

Key terms

Latency
How long one read or write takes. Smaller is better.
SRAM
Static RAM. Fast (a few ns) but big and costly per bit. Caches are made of it.
DRAM
Dynamic RAM. Cheap and dense, but slow (50–100 ns). Main memory is made of it.
Cache
A small, fast memory that keeps copies of recently used data from a bigger, slower memory.
Hit / miss
A hit means the data was already in the cache. A miss means it was not, so the CPU must fetch it from the slower level.
Memory wall
The growing speed gap between the CPU and DRAM.
Locality
Programs tend to use the same data again (temporal), and data that sits nearby (spatial).
Cycle counter
A counter inside the CPU that goes up by 1 every clock tick. Read it before and after some code to time that code.

1. The memory hierarchy

We cannot make memory that is fast, huge and cheap all at once. So computers stack several kinds. Each level down is roughly 10× (or more) slower, but much bigger and cheaper per GB.

1 ms = 1,000 µs = 1,000,000 ns. So a hard-disk read is about 10 million times slower than an L1 read.

2. The memory wall

From the 1980s until about 2005, CPU speed grew by roughly 50% per year. DRAM latency improved only about 7% per year. Compounded over the years, the gap became thousands of times. The CPU spends much of its time waiting for memory. This is the memory wall.

Why is DRAM slow?

  • Tiny capacitors. A DRAM bit is charge on a tiny capacitor. Sensing that tiny charge takes time.
  • Destructive read. Reading a DRAM cell drains it, so every read must write the value back.
  • Refresh. The charge leaks away, so every cell must be rewritten every few milliseconds.
  • Distance. DRAM sits on separate chips, outside the CPU, and signals must travel across the board.

SRAM keeps each bit in a loop of transistors, so it needs no refresh and reads in a few ns. See SRAM vs DRAM.

Growth after n years = (1 + rate)nAfter 20 years: CPU 1.520 ≈ 3,325× · DRAM 1.0720 ≈ 3.9× · gap ≈ 859×

3. Locality: why caches work

A cache only helps if the data we need next is probably already in it. Real programs make this true, in two ways.

Temporal locality (time)

"Used now, likely used again soon."

  • Loop code runs over and over.
  • A loop counter i or a running total is read and written every round.

So: keep recently used data in the cache.

Spatial locality (space)

"Used now, its neighbours are likely used soon."

  • Array elements are visited one after another.
  • Instructions run in order: PC, PC+4, PC+8 …

So: when you fetch one item, fetch a whole block of neighbours too.

python-like pseudocode · sum an arraycode → which locality
total = 0Make a variable called total and set it to 0.
for i in range(N):Repeat the indented line N times, with i = 0, 1, 2, … N−1. The loop code itself is reused: temporal.
total = total + arr[i]total and i are touched every round: temporal. arr[0], arr[1], … sit side by side: spatial.

4. Lab 5A: array vs linked list

Both hold N numbers and both are summed in N steps. Yet the array is usually much faster. The difference is where the items live in memory.

Array
Items stored in one unbroken row of memory. Item i is at start + i × size.
Linked list
Each item (a node) is stored wherever there was free space. It holds its value plus the address of the next node (a pointer).
python-like pseudocode · lab 5A traversalscode → what it means
# 1) array traversalA comment: a note for humans, ignored by the computer.
total = 0Start the running sum at 0.
for i in range(N):i takes the values 0, 1, …, N−1.
total = total + arr[i]Read the next element. It is right next to the last one, so it is usually already in the cache.
# 2) linked-list traversal
total = 0
node = headhead is the first node. node marks where we are.
while node is not None:Keep going until we fall off the end (None means "no next node").
total = total + node.valueAdd this node's number.
node = node.nextJump to the address stored in this node. That address can be anywhere, so this is often a cache miss.

Getting clean numbers

Run each test several times and keep the smallest or middle value. Use a large N (millions of items) so the data does not fit in the cache. For the list, the gap is biggest when nodes are created in a shuffled order, because then they really are scattered.

5. Lab 5B: row vs column traversal

Memory is one long line of bytes, so a 2D array must be flattened. C and Python/NumPy use row-major order: row 0 first, then row 1, and so on.

address of A[i][j] = start + (i × N + j) × sizeN = number of columns · size = bytes per element (8 for a typical number)
python-like pseudocode · lab 5Bcode → what it means
# row-wise (fast)
for i in range(N):Outer loop picks the row.
for j in range(N):Inner loop walks along that row. It changes fastest.
total = total + A[i][j]Address goes +1 element each time: great spatial locality.
# column-wise (slow)
for j in range(N):Outer loop picks the column.
for i in range(N):Inner loop walks down the column.
total = total + A[i][j]Address jumps +N elements each time: lots of cache misses once N is large.

Ballpark result: for small N (the whole array fits in cache) both orders take about the same time. For large N (thousands × thousands), column-wise is often several times slower. The exact ratio depends on the machine. The fix is simple: make the inner loop move along the row.

6. Cache-blocked (tiled) matrix multiply

Multiplying two big N × N matrices touches A, B and C in patterns that keep leaving the cache. Blocking (or tiling) cuts each matrix into small bs × bs tiles that fit in L1, and finishes one set of tiles before moving on.

python-like pseudocode · C = A × B, blockedcode → what it means
# plain version: C[i][j] += A[i][k] * B[k][j]Each answer cell is row i of A "times" column j of B.
bs = 32Tile size. Chosen so three tiles fit in L1 (see formula below).
for ii in range(0, N, bs):Jump through the rows in steps of bs: 0, 32, 64, …
for kk in range(0, N, bs):Same for k …
for jj in range(0, N, bs):… and for j. Together these pick one set of tiles.
for i in range(ii, min(ii+bs, N)):Now work only inside the chosen tile. min stops at the edge of the matrix.
for k in range(kk, min(kk+bs, N)):
for j in range(jj, min(jj+bs, N)):
C[i][j] += A[i][k] * B[k][j]Same maths as before. Only the visiting order changed, so the tile data stays hot in the cache.
3 × bs² × 8 bytes ≤ L1 sizeFor a 32 KB L1: bs² ≤ 32768 ÷ 24 ≈ 1365, so bs ≤ 36. A power of two such as 32 is a common choice.

Common mistakes & exam traps

Slips that cost marks
  • Mixing up the two localities: temporal = same item again, spatial = nearby items.
  • Saying a linked list is slow because it has "more elements". It has the same count; the scattered addresses are the problem.
  • Thinking row vs column order changes the answer. The sum is identical; only the speed changes.
  • C and NumPy are row-major. (Fortran and MATLAB are column-major, where the opposite order is fast.)
  • Units: 1 ms = 1,000 µs = 1,000,000 ns. Don't mix them up in comparisons.
  • The memory-wall chart is conceptual. Quote the growth rates (~50%/yr vs ~7%/yr), not exact numbers read off a graph.

Practice

A loop reads the variable count in every round. Which locality is this?

Temporal: the same item is used again and again in a short time.

Code reads arr[0], arr[1], arr[2] … Which locality?

Spatial: each read is next to the previous one in memory.

A 4-column array of 8-byte numbers starts at address 1000 (row-major). Where is A[2][3]?

1000 + (2 × 4 + 3) × 8 = 1000 + 11 × 8 = 1088.

CPU speed grows 50%/yr and DRAM 7%/yr. How big is the gap after 20 years?

1.520 ≈ 3,325 and 1.0720 ≈ 3.87. Gap ≈ 3,325 ÷ 3.87 ≈ 859×.

Main memory takes 100 ns and L1 takes 1 ns. How many times faster is L1?

100 ÷ 1 = 100× faster. That is why a hit in L1 matters so much.

Both an array and a linked list hold 10 million numbers. Why is summing the list slower?

List nodes are scattered in memory. Each node = node.next jumps to a far address that is probably not in the cache, so many reads are misses that wait ~100 ns for DRAM. Array elements are contiguous, so one miss loads a block of neighbours and the next reads are hits.

A column-wise loop is slow. How do you fix it without changing the result?

Swap the loops so the outer loop picks the row (i) and the inner loop walks the columns (j). Then memory is read in a straight line.

L1 is 48 KB and numbers are 8 bytes. What is the largest tile size bs so that 3 tiles fit?

3 × bs² × 8 ≤ 49,152 → bs² ≤ 2,048 → bs ≤ 45.25. So bs = 45 (or 32 if you want a power of two).
