Data races, atomic operations & mutexes

When two threads update the same variable at the same time, updates can silently get lost. The fix is to make the update atomic, meaning it happens as one step that can't be split. The CPU gives us tiny atomic instructions, and we build locks (mutexes) on top of them.

Think of it like this: two clerks share one tally sheet. Each reads the number (5), walks away to add 1 in their head, and comes back to write 6. Two visits should give 7, but the sheet says 6. A mutex is a single key to the room: only the person holding the key may touch the sheet.

Key terms

Thread / task
A separate line of work in a program. Several threads can run at the same time on different cores. FreeRTOS calls them tasks.
Shared variable
A piece of memory that more than one thread can read and write.
Data race
Two threads use the same variable at the same time, at least one of them writes, and nothing coordinates them.
Interleaving
The order in which the steps of different threads happen to mix together. It changes from run to run.
Critical section
The piece of code that touches shared data and must be run by only one thread at a time.
Mutual exclusion
The guarantee that at most one thread is inside the critical section.
Atomic
Done as one indivisible step. No other thread can see it half-finished.
Spinlock
A lock where a waiting thread keeps looping ("spinning") until the lock is free.
Mutex
A "mutual exclusion" lock. A waiting thread is put to sleep by the OS and woken up when the lock is free.
Deadlock
Two or more threads each wait forever for a lock that another one holds.

1. Why counter++ is not safe

counter++ means "add 1 to counter". It looks like one step, but the CPU does it in three steps. In MIPS (see C to MIPS) it becomes:

mips · what counter++ really iscode → what it means
lw $t0, counterLoad: copy counter from memory into the temporary register $t0.
addi $t0, $t0, 1Add: $t0 = $t0 + 1. This happens only in this thread's own register.
sw $t0, counterStore: write $t0 back to memory.

Each thread has its own registers, but both share memory. If the other thread's steps land in between these three, one update is lost:

Lab 6B: what you will see

  • Two tasks each run counter++ 100,000 times.
  • Expected: 2 × 100,000 = 200,000.
  • Actual (no protection): usually less than 200,000, and a different number each run. That randomness is the tell-tale sign of a race.
  • This can happen even on a single core, because the OS can pause a thread between the load and the store.

2. Critical sections and why a simple flag fails

The three steps form a critical section. We need mutual exclusion: only one thread inside at a time. The first idea is a flag, but it fails:

pseudocode · a broken lockcode → what it means
if lock == 0:Step 1: check whether the room is free.
lock = 1Step 2: mark it taken. But two threads can both pass step 1 before either reaches step 2, and then both enter.
# critical sectionNow two threads are inside. Mutual exclusion is broken.

The "check" and the "set" must happen as one atomic step. Software alone can't guarantee that, so the CPU provides special atomic instructions.

3. Hardware atomics: TAS and CAS

TAS: test-and-set

Sets the flag to 1 and returns its old value, all in one indivisible step.

  • It returns 0: the lock was free, and now you own it.
  • It returns 1: someone else holds it, so try again.

CAS: compare-and-swap

CAS(addr, expected, new): if the value at addr still equals expected, write new and return true. Otherwise change nothing and return false.

It means: "update only if nobody changed it since I looked".

pseudocode · a spinlock built from TAScode → what it means
while TAS(lock) == 1:Keep trying. Each try atomically sets lock = 1 and tells us if it was already 1.
passDo nothing, just loop again. This is the "spinning" (it wastes CPU time while waiting).
counter = counter + 1We got 0 back, so we own the lock. This is the critical section.
lock = 0Release: the next thread's TAS will now return 0.
pseudocode · lock-free increment with CAScode → what it means
loop:Repeat until it works.
old = xTake a snapshot of the current value.
if CAS(&x, old, old + 1):Atomically: "if x is still old, set it to old + 1". &x means "the address of x".
breakSuccess: leave the loop. If CAS failed, another thread changed x first, so loop and retry with the new value.

4. The build-up: atomics → spinlock → mutex

  1. Atomic instructionTAS / CAS from the CPU. Indivisible.
  2. SpinlockLoop on TAS. Good for very short waits, but it burns CPU while spinning.
  3. MutexTry the atomic first. If the lock is busy, ask the OS to sleep the thread and wake it later.

6. Correctness vs overhead

ApproachCorrect?SpeedWhy
UnsynchronizedWrongFastestNo coordination at all
Atomic (__atomic_fetch_add)CorrectSmall overheadOne special instruction per increment
MutexCorrectMost overhead per incrementA lock + unlock call every time, plus possible sleeps and wake-ups

This comparison is qualitative. Time your own runs in the lab; the exact ratios depend on the board and compiler.

Batching: the fastest correct option

Let each thread count in its own local variable (not shared, so no race), then add the total to the shared counter once at the end:

long local = 0; for (...) local++; then __atomic_fetch_add(&counter, local, __ATOMIC_SEQ_CST);

That is 1 synchronised operation instead of 100,000.

7. Pitfalls of locks

Deadlock

Thread 1 holds lock A and waits for B. Thread 2 holds B and waits for A. Both wait forever. It needs all four conditions:

  • Mutual exclusion: a lock has one owner at a time.
  • Hold and wait: a thread holds one lock while waiting for another.
  • No preemption: a lock can't be taken away.
  • Circular wait: a cycle of waiting.

Fix: always take locks in the same order. That breaks the cycle.

Priority inversion

A low-priority task holds a lock that a high-priority task needs. Meanwhile, a medium-priority task keeps running, so the high-priority task waits indirectly behind it.

Fix: priority inheritance. The lock holder temporarily gets the waiter's high priority. FreeRTOS mutexes do this; this is one reason to use a mutex rather than a plain semaphore.

Common mistakes & exam traps

Slips that cost marks
  • Thinking counter++ is one step. It is load, add, store.
  • Expecting the buggy result to be the same every run. It is random.
  • Building a lock from a normal "check then set". Only an atomic TAS/CAS makes it safe.
  • CAS does nothing when the value has changed. It returns false and you must retry.
  • Calling a spinlock a mutex. A spinlock busy-waits; a mutex sleeps.
  • Forgetting to unlock (for example on an early exit). Every other thread then waits forever.
  • Locking inside a tight loop and then being surprised it is slow. Batch instead.

Practice

Two threads each do counter++ 100,000 times with no lock. What result do you expect, and what do you get?

Expected 200,000. Actual: usually less, and different each run, because interleaved load-add-store sequences lose updates.

counter = 5. Show an interleaving of two increments that ends with 6.

A loads 5, B loads 5, A adds (6), B adds (6), A stores 6, B stores 6. The result is 6 instead of 7.

x = 7. What does CAS(&x, 5, 6) do?

7 ≠ 5, so it writes nothing and returns false. x stays 7.

lock = 0. Thread A calls TAS(lock), then thread B calls TAS(lock). What does each get back?

A gets 0 (it was free; A now owns it, and lock = 1). B gets 1 (busy), so B keeps waiting.

Why is a mutex better than a spinlock for long waits?

A spinlock burns CPU time looping. A mutex asks the OS to put the waiting thread to sleep, which frees the core for other work.

Rank unsynchronized, atomic and mutex by speed and by correctness.

Speed: unsynchronized > atomic > mutex. Correctness: only atomic and mutex are correct.

Name the x86, ARM and RISC-V atomic primitives.

x86 LOCK CMPXCHG. ARM LDREX/STREX. RISC-V "A" extension LR/SC (and AMO*).

Give a simple rule that prevents deadlock between two locks.

Every thread takes the locks in the same fixed order (always A, then B). That breaks the circular-wait condition.
