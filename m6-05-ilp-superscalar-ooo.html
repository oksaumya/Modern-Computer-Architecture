ILP: superscalar, out-of-order execution & register renaming

Even one core can do several instructions at once. It can run them side by side (superscalar), run them in whatever order their inputs become ready (out-of-order), and rename registers so that unrelated instructions stop blocking each other. This page is an overview.

Think of it like this: a restaurant kitchen gets orders in sequence. A smart kitchen cooks the quick salad while the steak is still grilling, instead of waiting. The waiter still serves the dishes in the order they were ordered. That serving step is the "commit in order".

Key terms

ILP
Instruction-level parallelism: running parts of different instructions at the same time inside one core.
IPC
Instructions per cycle (1 ÷ CPI). Above 1 means more than one instruction finishes per clock cycle. See performance.
Superscalar
A pipeline that fetches, decodes and executes several instructions in each stage.
Width
How many instructions a superscalar core can handle per stage (2-wide, 4-wide…).
Out-of-order (OoO)
Executing an instruction as soon as its inputs are ready, even if earlier instructions are still waiting.
Architectural register
A register the program sees, like $t0: one of the 32 in the register file.
Physical register
One of a larger hidden pool of real storage slots inside the CPU (r1, r2, …).
RAT
Register alias table: says which physical register currently holds each architectural register.
Reservation station
A waiting slot where an instruction sits until its inputs are ready.
ROB
Reorder buffer: a queue that holds finished results until they can be committed in program order.
Commit (retire)
Making a result official: writing it to the real register or memory.
Precise exception
When an error happens, everything before the faulting instruction is done and nothing after it is. The OS sees a clean state.

1. Three ways to get ILP

  1. PipeliningSplit each instruction into stages, like an assembly line (5-stage pipeline).
  2. SuperscalarMake every stage wider, so several instructions move through side by side.
  3. Dynamic schedulingLet the hardware reorder instructions at run time (OoO + renaming).

2. Superscalar: IPC above 1

A 2-wide pipeline copies the stage hardware, so two instructions enter each stage together:

Cycles for N instructions ≈ stages + (⌈N ÷ width⌉ − 1)10 instructions: scalar = 5 + 9 = 14 cycles · 2-wide = 5 + (5 − 1) = 9 cycles

In practice IPC stays well below the width. Dependencies between instructions, branch mispredictions and cache misses all get in the way. That is what OoO tries to fix.

3. Out-of-order execution (Tomasulo-style)

A simple pipeline stalls everything behind a slow instruction (for example a load that misses the cache). An OoO core lets later instructions go ahead, as long as they don't need the slow one's result. The idea comes from Robert Tomasulo's algorithm (IBM, 1967). The reorder buffer was added later to keep exceptions precise.

4. Register renaming

Recall the data dependencies from hazards. Only one kind is a real dependency:

NamePatternReal?
RAW (read after write)A later instruction reads a register an earlier one writesTrue dependency: it needs that value
WAW (write after write)Two instructions write the same registerFalse: they only share a name
WAR (write after read)A later instruction overwrites a register an earlier one readsFalse: they only share a name

False dependencies exist only because there are just 32 register names. Renaming gives each new write its own fresh physical register, so the name clash disappears.

Worked example

mips · original codecode → what it means
I1: add $t0, $t1, $t2$t0 = $t1 + $t2. ($t registers are temporary working registers.)
I2: sub $t3, $t0, $t4$t3 = $t0 − $t4. Reads I1's $t0: RAW, true.
I3: add $t0, $t5, $t6$t0 = $t5 + $t6. Writes $t0 again: WAW with I1, and WAR with I2. Both are false.
I4: or $t7, $t0, $t3$t7 = $t0 OR $t3. Needs I3's $t0 and I2's $t3: true.

There are 7 free physical registers, r1–r7. Inputs that nobody writes here ($t1, $t2, $t4, $t5, $t6) are already available. Each write takes the next free register, and the RAT is updated:

Instr.RenamedRAT changeFree list after
I1r1 = t1 + t2t0 → r1r2 … r7
I2r2 = r1 − t4t3 → r2r3 … r7
I3r3 = t5 + t6t0 → r3 (a new name!)r4 … r7
I4r4 = r3 | r2t7 → r4r5, r6, r7
What happens to the "real" $t0?

At commit, the architectural register $t0 takes the value of r3 (the last write to it). I1's r1 is freed once nothing needs it any more. The program never notices any of this.

5. Branch prediction and speculation

  • An OoO core fetches far ahead, past branches it hasn't resolved yet. It predicts the direction (see branch prediction) and executes speculatively.
  • The ROB makes this safe. On a mispredict, every instruction after the branch is squashed (thrown away) before it commits.
  • But squashed instructions can still leave traces in the cache. That is exactly what Spectre and Meltdown exploit.

6. The limits of ILP

Power wall

Renaming tables, big ROBs, wide decoders and many reservation stations use lots of transistors and energy, and much of it only does bookkeeping. See power wall.

Diminishing returns

Real programs have limited ILP: branches, true dependencies and memory waits. Doubling the width gives far less than double the IPC. Mispredictions throw away more work in deeper, wider pipelines. So designers turned to more cores instead.

Common mistakes & exam traps

Slips that cost marks
  • OoO executes out of order, but commits in order. Say both halves.
  • Only RAW is a true dependency. WAW and WAR are name dependencies, and renaming removes them.
  • Superscalar ≠ multicore. Superscalar is one core running several instructions per stage.
  • The ROB is what makes exceptions precise, not the reservation stations.
  • IPC can exceed 1 only in a superscalar design. A plain scalar pipeline gives IPC ≤ 1.
  • Renaming doesn't create more architectural registers. The program still sees 32.

Practice

A 5-stage, 2-wide pipeline runs 8 instructions with no stalls. How many cycles? What would a scalar pipeline need?

2-wide: 5 + (4 − 1) = 8 cycles. Scalar: 5 + (8 − 1) = 12 cycles.

Name the dependency: I1 writes $s0; I2 writes $s0 (and doesn't read it).

WAW, a false (name) dependency. Renaming gives each write its own physical register.

Why does an OoO core need a reorder buffer?

To commit results in program order. Then exceptions are precise, and mispredicted (speculative) work can be thrown away before it becomes visible.

Rename: I1: add $t0,$t1,$t2 · I2: add $t0,$t0,$t3 · I3: sub $t4,$t0,$t1, using free list r1, r2, r3.

I1: r1 = t1 + t2 (t0 → r1). I2: r2 = r1 + t3 (t0 → r2). I3: r3 = r2 − t1 (t4 → r3). I3 correctly uses the latest t0, which is r2.

What are reservation stations for?

They hold decoded instructions until all their inputs are ready. Then the instruction is sent to a free execution unit, regardless of program order.

Why did the industry stop making cores ever wider?

Diminishing returns (limited ILP in real code, mispredictions) and the power cost of the extra bookkeeping hardware. More cores gave more performance per watt.
