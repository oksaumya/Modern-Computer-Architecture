Spectre & Meltdown: when speed tricks leak secrets

In 2018, researchers showed that speculative execution can be tricked into touching secret data. The CPU throws the wrong results away, but the cache still remembers what was touched. By timing memory accesses, an attacker can read that secret back.

Think of it like this: a librarian fetches a book before checking whether you are allowed to read it. When the check fails, she puts it back, but it now sits on the "recently used" shelf by the desk. You can't read it, but you can notice which book is on that shelf, because it comes back instantly when you ask for it.

Key terms

Speculative execution
Running instructions before the CPU knows they are needed (for example, past an unresolved branch). See OoO.
Transient instructions
Instructions that ran speculatively and were then squashed. Officially they never happened.
Side channel
Leaking information through a side effect (timing, power, cache state) instead of the normal output.
Flush+Reload
A cache timing trick: empty some cache lines, let the victim run, then time which lines became fast.
Bounds check
An if that makes sure an array index is inside the array.
Kernel memory
Memory used by the operating system. User programs must never read it.
KPTI
Kernel Page Table Isolation: the Meltdown fix that hides kernel memory from user page tables.
Retpoline
A compiler trick that stops the CPU from guessing where indirect jumps go (the Spectre v2 fix).

1. The ingredients

  1. Branch predictionThe CPU guesses a branch's direction (prediction).
  2. SpeculationIt runs ahead on that guess (OoO).
  3. SquashA wrong guess is thrown away, but only the architectural state (registers, memory) is undone.
  4. Cache stays warmThe data loaded during speculation is still in the cache (cache).
  5. Timing leakCached memory reads are much faster, and that can be measured.

2. Flush+Reload: reading the cache by timing

  1. Flush: the attacker removes 256 specific memory pages (one per possible byte value 0–255) from the cache. On x86 there is even an instruction for this: clflush.
  2. Victim runs: it (speculatively) reads the page whose number equals the secret byte. That page gets loaded into the cache.
  3. Reload: the attacker reads all 256 pages and times each read. 255 are slow (DRAM). One is fast (cache). Its number is the secret.

3. Spectre variant 1: bounds check bypass

The victim code is ordinary, correct-looking C. It is explained line by line below; no C knowledge is needed.

c · victim functioncode → what it means
if (x < array1_size)"Only if x is smaller than the size of array1…" This is the bounds check. It makes sure x is a valid position.
y = array2[array1[x] * 4096];"…read the number at position x of array1, multiply it by 4096, and read array2 at that position." array[i] means "item number i of the array".

Why 4096? It is the size of one memory page. Multiplying by 4096 sends each possible byte value (0–255) to a different page of array2, so the Flush+Reload step can tell the values apart.

The attack, step by step

1. Setup. Say array1 has 16 items (array1_size = 16). Somewhere else in the same program's memory is a secret byte, 75 ('K'). array2 is 256 pages big.

2. Train the predictor. The attacker calls the function many times with valid x values (0–15). The check always passes, so the branch predictor learns "this if is always true".

3. Flush. The attacker makes sure none of array2's 256 pages is in the cache. (Also, if array1_size itself isn't cached, the check will be slow to finish, which gives speculation more time.)

4. Attack call. The attacker passes a huge, out-of-bounds x, chosen so that array1[x] lands exactly on the secret byte. The CPU hasn't finished comparing x with array1_size yet, so it predicts "true" and runs the body speculatively.

5. Speculative reads. array1[x] reads the secret: 75. Then array2[75 × 4096] = array2[307200] is read, so page 75 is now in the cache.

6. Squash. The comparison finishes: x ≥ 16, so the guess was wrong. The CPU throws away y and continues correctly. No register or memory value changed, but the cache still holds page 75.

7. Reload. The attacker times reads of all 256 pages. Page 75 is fast, so the secret byte = 75 = 'K'. Repeat with x + 1, x + 2, … to read the secret byte by byte.

4. Meltdown: reading kernel memory

For speed, operating systems used to map kernel memory into every program's page table, marked "kernel only" (see virtual memory). Meltdown abuses that:

pseudocode · Meltdown corecode → what it means
v = read_byte(kernel_address)Illegal! A user program reading kernel memory. The CPU will raise a fault, but only when this instruction commits.
y = array2[v * 4096]On affected CPUs, OoO execution has already fetched v and runs this line before the fault is handled. The page for v gets cached.
# fault arrives, results squashedThe attacker catches the fault (or avoids it), then uses Flush+Reload to learn v.
  • It needs no mistrained branch: the permission check simply arrives too late.
  • It mostly affected Intel CPUs of that era (some ARM and IBM designs too). Most AMD CPUs were not affected.
  • Fix: KPTI. User-mode page tables no longer map (almost any) kernel memory, so there is nothing to read transiently. The cost: every system call must switch page tables.

The performance cost

The fixes remove or limit exactly the speed tricks that made CPUs fast. How much it costs depends heavily on the workload. Programs that make many system calls (file and network I/O, databases) were hit hardest by KPTI, especially on older CPUs without PCID support (a feature that makes page-table switches cheaper). Ordinary desktop use was affected much less. Newer CPUs fix much of this in hardware, which lowers the cost.

The big lesson

Lecture L09 said von Neumann's "programs are data" idea is also the root of whole classes of security exploits. Spectre and Meltdown add a second lesson: any shared, hidden state (caches, predictors) that speeds things up can also leak information. Security is now an architecture problem, not only a software one.

Common mistakes & exam traps

Slips that cost marks
  • Spectre and Meltdown are not bugs in one program. They come from how the hardware speculates.
  • Squashing undoes registers and memory but not the cache state. That is the whole leak.
  • Meltdown = the permission check comes too late; Spectre = a mistrained branch predictor.
  • KPTI fixes Meltdown; retpoline fixes Spectre v2; lfence / masking fix Spectre v1.
  • The attacker never reads the secret directly. They infer it from timing.
  • The ×4096 exists to spread byte values across different pages. It is not part of the "real" program logic.

Practice

In Spectre v1, the secret byte is 0x41 ('A' = 65). Which array2 offset gets cached?

65 × 4096 = 266,240, which is page 65 of array2.

Why does the attacker train the branch predictor first?

So the CPU predicts "bounds check passes" and runs the body speculatively even for the out-of-bounds x.

The CPU squashes the speculative instructions. Why is the secret still leaked?

Squashing restores registers and memory, but the cache still holds the page loaded during speculation. Timing reveals which page it was.

Give one fix each for Meltdown, Spectre v1 and Spectre v2.

Meltdown: KPTI. Spectre v1: lfence after the check, or index masking. Spectre v2: retpoline (or IBRS microcode).

Why did KPTI slow down databases more than video games?

KPTI adds a page-table switch to every system call. Databases make huge numbers of system calls (I/O). Games spend most of their time computing in user mode.

Spectre or Meltdown: "a user program reads OS memory because the permission fault is handled too late"?

Meltdown.

Wrap-up: name three places in this course where parallelism was used for speed.

Any three of: carry look-ahead adders (carries in parallel), pipelining, superscalar/OoO, multicore, SIMD, GPUs.
